# 추가 구현 후보

현재 구현은 로컬에서 동작하는 MVP입니다. 다음 기능들을 추가하면 실제 사용성, 안정성, 운영성이 좋아집니다.

## 우선순위 높음

1. 지역 모호성 처리
   - `중앙동`, `시청`, `터미널 근처`처럼 여러 지역이 가능한 입력에 대해 후보 지역을 제시합니다.
   - 예: “서울시청, 부산시청, 대전시청 중 어디인가요?”

2. Ollama JSON 파싱 안정화
   - 모델 응답이 JSON이 아닐 때 재시도 프롬프트를 한 번 더 보냅니다.
   - `area`, `food`, `conditions`의 타입 검증을 강화합니다.

3. NAVER API 실패 메시지 개선
   - 401, 403, 429, 5xx를 구분해 사용자와 개발자에게 다른 메시지를 제공합니다.
   - 현재는 대부분 `NAVER_API_ERROR`로 묶입니다.

4. 검색 결과 없음 처리
   - 후보가 0개일 때 음식 키워드를 완화하거나 지역만으로 재검색합니다.
   - 사용자에게 “검색 범위를 넓혀볼까요?” 같은 후속 제안을 반환합니다.

5. 프론트엔드 UI 개선
   - 로딩/오류/빈 결과 상태를 명확히 표시합니다.
   - 거리, 카테고리, 전화번호, 지도 링크를 더 보기 좋게 카드화합니다.

## 우선순위 중간

1. 캐싱
   - 같은 지역/음식 검색은 일정 시간 캐시합니다.
   - NAVER API 호출량과 응답 시간을 줄입니다.

2. 선호 조건 필터
   - 혼밥, 데이트, 가성비, 주차, 카페, 술집 같은 조건을 명시적으로 필터링합니다.
   - 현재는 키워드 점수와 후속 제안 수준입니다.

3. 추천 이유 개선
   - 현재 이유는 키워드/카테고리/거리 중심입니다.
   - 장소별 카테고리와 조건을 더 잘 연결하는 템플릿을 추가할 수 있습니다.

4. 설정 검증 명령
   - `python -m app.check_config` 같은 진단 명령을 만들어 Ollama/NAVER 연결을 한 번에 확인합니다.

5. API 테스트 확장
   - NAVER API 응답 mock을 추가해 성공 경로 통합 테스트를 보강합니다.

## 우선순위 낮음

1. 사용자 검색 기록
   - 최근 검색 지역과 선호 조건을 저장합니다.

2. 데이터베이스 도입
   - 즐겨찾기, 로그, 캐시를 저장하려면 SQLite 또는 PostgreSQL을 붙입니다.

3. 배포
   - 로컬 Ollama 의존성이 있어 일반 클라우드 배포 전 모델 실행 위치를 결정해야 합니다.
   - 후보: 로컬 전용 앱, 사내 서버, GPU 서버, Ollama가 떠 있는 별도 호스트.

4. 진짜 tool-calling agent 구조
   - `search_local`, `geocode`, `rank_restaurants`를 tool로 감싸고 모델이 호출 순서를 결정하게 만들 수 있습니다.
   - 현재 요구사항에서는 고정 파이프라인이 더 단순하고 디버깅하기 쉽습니다.

## 지금 바로 확인할 체크리스트

- `.env`에 `NAVER_API_HUB_CLIENT_ID`, `NAVER_API_HUB_CLIENT_SECRET`이 있는가?
- Ollama가 `http://127.0.0.1:11434`에서 실행 중인가?
- `ollama list`에 `qwen3.5:4b`가 있는가?
- `GET /health`에서 `hasNaverSearchKeys`가 `true`인가?
- `POST /api/recommend`에서 후보가 1개 이상 나오는가?
