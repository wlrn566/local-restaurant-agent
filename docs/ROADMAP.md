# 구현 현황과 다음 작업

## 구현 완료

- FastAPI 추천 API와 브라우저 채팅 화면
- NAVER API HUB 지역 검색, 검색 결과 정렬
- Ollama 문장 파싱과 추천 응답 생성
- Ollama 연결 실패 시 규칙 기반 검색 파싱과 기본 응답 사용
- 검색 로딩, 오류, 빈 결과 안내
- 채팅에 번호가 있는 추천 가게 목록 표시
- 가게 이름 전체 또는 일부로 선택하고, 모호한 선택은 후보를 다시 확인
- 예약에 필요한 날짜·시간·인원 누락 여부를 묻고 네이버 지도 링크 안내
- 도로명 주소를 사용한 네이버 지도 검색 링크

## 다음 우선순위

### 높음

1. 예약 서비스 연동 검토
   - 현재 앱은 예약을 제출하지 않고 네이버 지도로 연결합니다.
   - 실제 예약을 자동화하려면 대상 서비스, API 사용 권한, 필요한 예약 정보, 개인정보 처리 방식을 정해야 합니다.

2. 검색 입력 파싱 보강
   - Ollama가 꺼졌을 때 규칙 기반 파서는 제한된 음식·조건 단어에 의존합니다.
   - 지역명과 요청 표현을 더 넓게 처리하고, 파싱 결과를 회귀 테스트로 고정합니다.

3. 지역이 모호한 경우 되묻기
   - 같은 이름의 역·동·구가 여러 지역을 뜻할 수 있습니다.
   - 후보 지역을 사용자에게 보여주고 선택받는 단계를 추가합니다.

4. 네이버 API 오류 안내 세분화
   - 401/403 인증·권한 오류, 429 호출 제한, 5xx 서비스 오류를 사용자 안내와 로그에서 구분합니다.

### 중간

1. 검색 결과 품질 개선
   - 음식 키워드가 포함된 검색이 0건이면 지역 기반 검색으로 한 번 넓혀 검색합니다.
   - 일반 맛집 검색에서 카페 등 원치 않는 업종을 제외하는 필터를 검토합니다.

2. 검색 결과 정보 보강
   - 거리 좌표와 영업시간 등 제공 가능한 데이터를 확인하고, 검증된 항목만 화면에 표시합니다.
   - 평점이나 리뷰 수는 API가 제공하지 않으면 추정하거나 생성하지 않습니다.

3. UI 접근성과 대화 상태
   - 키보드 탐색, 스크린리더 안내, 모바일에서 긴 대화의 사용성을 점검합니다.
   - 대화 유지가 필요하면 브라우저 저장 또는 사용자 계정 기반 저장 방식을 선택합니다.

4. 호출 효율 개선
   - 반복 검색 캐시와 NAVER/Ollama 응답 시간 지표를 추가합니다.

### 낮음

1. 즐겨찾기와 검색 기록 저장
2. 설정 진단 명령과 운영용 상태 점검
3. 로컬 Ollama를 포함한 배포 방식 결정
4. 실제 필요가 생기면 고정 파이프라인을 tool-calling 구조로 확장

## 확인 항목

- `.env`에 NAVER API HUB 검색 키가 설정되어 있는가?
- Ollama를 사용하는 경우 `ollama list`에서 `qwen3.5:4b`를 확인할 수 있는가?
- `/health`에서 `hasNaverSearchKeys`가 `true`인가?
- `/api/recommend`가 입력 지역과 음식에 맞는 결과를 반환하는가?
- 예약 대화가 가게 선택, 날짜, 시간, 인원 확인 후 지도 링크로 이어지는가?
